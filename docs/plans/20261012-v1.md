# v1: release actions for Rust repos

Extract the release steps that wavo, macmon, unjar and badgelib each copy (and that drifted) into
four actions and tag `v1`. Another agent then moves the repos onto them from this repo's docs, so
the readme must be enough to migrate wavo with the same behaviour. npm/PyPI and Homebrew come
later.

The reference is wavo's `.github/workflows/main.yml`: `release-check` (read-only), `release`
(`contents: write`, `id-token: write`, `attestations: write`), `dev` / `dev-release`.

## Design

- **Why actions, not a reusable workflow.** Jobs, `permissions:` and the build stay visible in
  each repo, and the read-only-build / write-only-publish split stays per repo. Trusted Publishing
  works either way (crates.io matches `workflow_ref`, the caller's file), but PyPI rejects
  reusable workflows.
- **Runtime.** `node24` JavaScript actions with `main: index.ts`, run by the runner's bundled Node
  24 (type stripping is stable there). No `dist/`, no npm dependencies at runtime (the toolkit's
  octokit isn't on the runner; actions bundle it). GitHub through `gh`, preinstalled on the hosted
  runners, with a `token` input defaulting to `${{ github.token }}`; `git` for tags.
- **Attestation** is an `actions/attest@v4` step in the caller, after `github-release` /
  `dev-release`, on the files they output.
- **Trigger.** Only the `release: vX.Y.Z` commit title (a trailing ` (#N)` stripped). The caller
  gates its release jobs with `if: startsWith(github.event.head_commit.message, 'release:')`.

## Actions

1. `release-check`: inputs `manifest` (auto: `Cargo.toml`, `pyproject.toml`, `package.json`),
   `changelog` (default `changelog.md`). Title must equal `release: v` + the manifest's version.
   Notes are the `## vX.Y.Z` section, matched by exact tag (not a regex), without `---`, and must
   have a `- ` bullet. Outputs `tag`, `version`, `notes`, `notes-file`.
2. `github-release`: inputs `tag`, `notes`, `files` (glob), `rename-from` / `rename-to` (e.g.
   `wavo-dev-` → `wavo-v1.2.3-`). Fails if the tag exists on another commit, else pushes it;
   creates the release or uploads only missing assets. Outputs `files`.
3. `dev-release`: inputs `tag` (default `dev`), `files`, `title`, `notes` (default: the build's
   commit and time). Skips when `main` has moved past `GITHUB_SHA`; moves the tag and replaces the
   pre-release's assets. Outputs `files`.
4. `crates-publish`: skips when the version is already on crates.io, else `cargo publish --locked`
   with the `token` from `rust-lang/crates-io-auth-action` in the step before (which also revokes
   it). `no-verify` and `dry-run` inputs.
